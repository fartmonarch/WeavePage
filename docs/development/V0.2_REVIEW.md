# V0.2 开发记录、待优化项与收尾验收

记录日期：2026-10-20。

状态：模型接入已由开发者手动运行成功；V0.2 收尾检查待完成。本文不代表所有异常分支、生成源码的编译结果或动画行为均已验证。

## 1. 当前实现与边界

- Web 提交 `description`，调用 FastAPI 的 `POST /api/generate`。
- 后端使用 OpenAI Python SDK 的异步客户端调用 DeepSeek；API Key 只从后端配置读取。
- 当前模型为 `deepseek-flash`，使用 JSON 模式，关闭思考模式，`temperature=0.2`，`max_tokens=16384`。
- 当前请求超时配置为 120 秒；SDK 自动重试设置为 0，应用尚无自动修复或重试循环。
- 模型生成 `component_name`、`summary`、`code`；后端解析 JSON 并用 Pydantic 校验，成功后添加自己的 `request_id`。
- 提示词要求 React + TypeScript 单文件组件、命名导出且名称匹配 `component_name`、只依赖 React。
- 源码要求目前主要依靠提示词。Pydantic 只校验字段、类型和字符串长度，不能证明源码可编译、导出匹配、依赖合规或行为正确。
- 当前只展示源码，没有隔离预览、组件检索、多轮修改、自动修复或保存导出功能。

## 2. 已观察到的问题与处理记录

### 2.1 输出预算耗尽

证据：开发者用 Text Scramble 标题组件需求请求时，先后在 `max_tokens=4096` 和 `8192` 下遇到 `finish_reason=length`。

已处理：在 JSON 解析之前检查结束原因，单独指出输出达到上限；后续将预算改为 16384，并调整思考模式和请求超时。

尚不确定：没有记录当次 token usage、推理用量和最终源码长度，不能认定该组件源码本身必然需要超过 8192 token。多项设置与提示词均曾改变，不能把后续成功完全归因于某一个参数。

### 2.2 JSON 解析失败与错误提示过于笼统

证据：开发者遇到 JSON 第 1 行第 2407 列解析失败；此前空响应、解析错误和字段校验错误被合并为同一条提示。检查中也发现提示词示例曾包含不合法的引号或字符串片段。

已处理：分开判断空 choices、空 content、输出截断、JSON 解析失败及 Pydantic 校验失败；使用 Python 字典加 `json.dumps()` 构造合法 JSON 示例。开发者随后反馈请求成功。

尚不确定：未取得该次失败位置的实际响应片段，不能确认第 2407 列具体是哪一种字符错误，也不能据一次成功认定 JSON 问题已永久消除。

### 2.3 Text Scramble 组件功能不完整

证据：开发者提供的生成代码声明了 `speed` 参数，但动画逻辑没有读取它。这个结论来自所提供源码的静态检查，尚无隔离预览运行记录。

首次显示内容、空格是否参与扰乱、等宽字体是否可覆盖属于效果和接口设计选择，应先明确预期，再验收。“进入视口才播放”未出现在最初提供的需求中，不能将其直接计为遗漏功能。

命名导出符合当前提示词约定，未提供默认导出不是本次生成错误。React 新 JSX 转换配置下不必额外导入默认 `React`。不能直接把 `display` 加入动画 effect 的依赖数组，否则可能导致每次状态更新重新启动动画。

## 3. 后续优化清单

| 问题 | 建议阶段 | 处理方向 | 验收依据 |
| --- | --- | --- | --- |
| 字段合规但源码可能不编译，参数可能声明后未使用 | V0.3 | 在隔离预览前加入 TSX 编译和诊断；按配置使用静态检查规则 | 能区分生成、编译和运行失败；未使用参数能被相应规则指出；编译通过不等于行为正确 |
| 命名导出、名称和 React 依赖尚未强制验证 | V0.3 | 确定预览入口，校验导出和依赖，统一加载规则 | 命名导出组件能按契约加载；不支持的依赖得到明确诊断 |
| 动画等行为需求没有可检查的条件 | V0.3 起持续改进 | 为代表性组件写清交互预期，如速度、初始状态和空格处理 | 调整 speed 能观察到效果变化，动画按已明确的需求触发并清理资源 |
| 预算、思考模式与生成质量的取舍缺少数据 | V0.2 收尾记录，后续评估 | 记录模型版本、提示词版本、结束原因、耗时及 usage；用相同用例比较设置 | 基于多次同条件样本比较成功率、耗时和消耗，不能用单次结果推断因果 |
| 日志直接打印模型内容片段，失败请求没有自己的关联 ID | V0.2 收尾精简日志，后续完善 | 移除常态内容片段打印；后续在请求开始生成 ID，记录阶段与错误类别 | 日志能关联成功和失败请求；默认不包含密钥或完整用户/模型内容 |
| 不同模型服务错误被合并处理 | 后续迭代 | 内部区分认证、连接、限流、超时、输出无效；区分开发诊断和用户提示 | 故障有可追踪类别；对外返回可读信息，不泄露供应商敏感错误 |
| 模型输出无效时没有恢复路径 | V0.5 | 基于明确失败类别做次数、时间与 token 均有上限的修复或重试 | 达到上限后停止，保留失败原因；不执行无界重试 |
| Python 与 TypeScript 响应类型仍手工同步 | 后续契约建设 | 从 FastAPI OpenAPI 生成类型或客户端 | 接口变化可同步到前端，减少字段漂移 |
| 生成质量缺少可重复评估 | V0.6，提前沉淀样例 | 保存需求和行为预期，逐步加入格式、编译和行为检查 | 每次调整提示词或模型后可对照固定用例，指标有样本和统计口径 |
