# 织页（WeavePage）项目蓝图

> 文档版本：1.0  
> 更新日期：2026-10-19  
> 目标读者：项目开发者（用于跟踪进度、拆分版本和向 AI 提出具体开发任务）

## 1. 项目定位

织页是一个面向前端开发者的 **React 组件生成与迭代工作台**。用户用自然语言描述组件，系统检索有来源的组件参考，生成 React + TypeScript 组件，在隔离环境中预览，并支持多轮修改、版本保存和代码导出。

**核心闭环：** 描述需求 → 检索参考 → 生成组件 → 校验并预览 → 对话迭代 → 保存 / 导出。

本项目同时承担两个目标：

1. 完成一个可部署、可演示、可在简历中如实描述的全栈项目。
2. 通过可逐步检查的实现过程学习 Agent 工作流、RAG、结构化输出、评估、安全边界和可观测性。

项目的区分度来自这条完整的 **“检索有来源、生成有约束、预览有隔离、修改有状态、结果可复现”** 工作流，而不是单纯调用模型生成一段 JSX。首版只做单个 React 组件，把完整闭环做可靠，再扩展为页面或多文件项目。

## 2. 产品范围与边界

### 首个可展示版本必须包含

- React + TypeScript 工作台：需求输入、Agent 阶段状态、代码、预览和错误反馈。
- FastAPI API：输入校验、统一响应和可读错误；模型密钥只放在后端环境变量。
- React 组件生成：限定单文件组件和明确的输出契约；输出先经 Pydantic / schema 校验。
- 组件参考检索：从少量精选资料开始，显示标题、来源链接、许可证和适用技术。
- 隔离预览：只运行受支持的代码形态与依赖；展示编译结果和诊断信息。
- 对话修改：围绕当前组件和当前会话继续迭代，不能每轮丢失上次结果。
- 保存和导出：至少可以导出当前 `.tsx` 源码；持久化先以明确、简单的方案实现。

### 明确暂缓

- React Native App、账户/团队协作、权限系统和多租户。
- 任意 npm 依赖、任意 shell / Python 执行、任意仓库写入。
- 无限制互联网爬取、自动复制未确认许可的开源代码。
- 多 Agent、自主规划式通用 Agent、多模型路由、MCP、Redis、微服务拆分。
- 页面级/多文件应用生成和“生产级”安全、弹性或规模承诺。

## 3. 技术方向与架构决策

| 领域     | 当前决策                                                             | 采用条件 / 暂缓项                                                          |
| -------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Web      | React + TypeScript + Vite                                            | 一个响应式 Web 应用同时支持桌面与手机浏览器；H5 不需要 React Native        |
| Monorepo | pnpm 管理 TypeScript 应用与包                                        | Python 服务独立由 `uv` 管理，不纳入 pnpm workspace                         |
| API      | Python + FastAPI + Pydantic，由 `uv` 管理依赖、虚拟环境和锁文件      | 保持单体 API；按职责分模块，不提前拆服务                                   |
| Agent    | 先实现可观察的单条工作流；在需要显式状态、分支、恢复时引入 LangGraph | 模型供应商通过薄适配层接入；只有确有收益再加 LangChain，不把框架数量当成果 |
| 检索     | 先用带元数据的精选本地目录和确定性检索                               | 有数据量、语义召回需求和评估集后再上 PostgreSQL / pgvector                 |
| 预览     | 先做小型技术验证，确认可行的隔离运行方式再定型                       | iframe 的视觉隔离不等于安全沙箱；不得在主应用上下文直接执行模型生成代码    |
| API 契约 | FastAPI OpenAPI 为接口事实来源                                       | 后续生成 TypeScript contracts / client；不手工维护两套互相漂移的 DTO       |
| 跨端     | 未来新增 Expo + React Native 应用                                    | 共享 API 契约、数据逻辑和 tokens；DOM UI 不假定能直接移植 RN               |
| 设计系统 | 先定义平台无关的基础 Design Tokens                                   | 有第二个平台或多个消费者后再抽成稳定共享包                                 |

### Monorepo 目标结构

下面是分阶段形成的**目标结构**，不是要求现在一次性创建所有空目录。每个目录在对应功能即将实现时再加入真实职责、README 或代码，避免空壳架构。

```text
weavepage/
├─ apps/
│  ├─ web/                         # 当前：React + TypeScript + Vite 工作台
│  ├─ api/                         # 当前：FastAPI 服务，独立使用 uv
│  │  ├─ app/
│  │  │  ├─ api/v1/                # HTTP 路由 / 依赖注入
│  │  │  ├─ core/                  # 配置、日志、错误处理
│  │  │  ├─ schemas/               # Pydantic 请求/响应契约
│  │  │  ├─ services/              # 用例编排、生成服务
│  │  │  ├─ agent/                 # 工作流状态、节点、提示词（达到阶段后创建）
│  │  │  ├─ retrieval/             # 资料源、检索和许可元数据（达到阶段后创建）
│  │  │  └─ main.py                # FastAPI 应用入口
│  │  └─ tests/                    # API 单元与集成测试（达到阶段后建立）
│  └─ mobile/                      # 后续：Expo + React Native
├─ packages/
│  ├─ contracts/                   # 从 OpenAPI 生成的 TS 类型 / 客户端
│  ├─ shared/                      # 前端 API 调用和纯业务逻辑
│  ├─ tokens/                      # 跨平台颜色、间距、字体等 token 源
│  └─ ui/                          # 有实际复用需求后再建立；不提前追求 DOM/RN 共用组件
├─ docs/
│  ├─ plan/WEAVE_PAGE_PLAN.md      # 项目目标与版本验收蓝图
│  ├─ adr/                         # 影响后续的架构决策及取舍
│  └─ development/                 # 运行、演示、迭代记录等短文档
├─ pnpm-workspace.yaml             # 仅纳入 apps/* 和 packages/*
└─ README.md
```

**目录规则：** `apps/api` 是与 Web、Mobile 并列的可运行应用，但 Python 依赖仍由 uv 管理，不属于 pnpm 包；pnpm workspace 只负责带 `package.json` 的 JavaScript/TypeScript 包。前端和后端通过 HTTP/OpenAPI 合作。`apps/mobile` 在 Web API 和共享纯逻辑稳定后才创建。`.web.tsx` / `.native.tsx` 仅在同一个共享组件确有平台分支时采用。

## 4. 版本路线图与完成标准

每个版本单独开发、单独对话；一个版本只完成一个可运行的垂直增量。下面里程碑可以跨越多天，不承诺 Agent 功能在五天内达到生产级。

| 版本                                   | 目标与学习重点                                               | 完成标准                                                                                                    |
| -------------------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| **V0.1 脚手架与 API 垂直切片**（当前） | workspace 边界、FastAPI 路由、CORS、HTTP/JSON、OpenAPI       | Web 输入描述，调用 API，显示固定但符合最终响应结构的结果；错误和加载状态可见；两端启动说明可复现            |
| **V0.2 可靠的模型生成**                | Provider 适配、提示词、Pydantic 结构化结果、超时和错误映射   | 后端调用一种模型；返回经过校验的 React 组件源文件与摘要；密钥不发给浏览器；失败时有明确错误                 |
| **V0.3 编辑与隔离预览**                | React/TSX 编译、诊断映射、运行边界                           | 支持范围内的单组件可以预览；语法/编译错误可见；模型代码不在主应用权限上下文执行；有明确依赖白名单和资源限制 |
| **V0.4 组件目录检索**                  | 资料结构、metadata filter、RAG 基本评估、许可溯源            | 从精选资料中检索可解释的参考；界面展示来源/许可证；至少有一组可重复的检索案例与预期结果                     |
| **V0.5 多轮 Agent 工作流**             | LangGraph StateGraph（如确认使用）、状态传递、分支、有限重试 | 用户修改基于当前代码/会话；可观察“解析→检索→生成→校验→必要修复”；修复次数封顶，保留过程结果和失败原因       |
| **V0.6 保存、导出与可回归验证**        | 数据持久化、版本模型、导出、基本 evals / 观测                | 重启后仍可恢复已保存版本；导出的组件能独立使用；固定用例可回归生成格式、检索相关性和预览成功率              |
| **V1.0 作品集发布**                    | README、部署、演示、安全边界、简历表述                       | 干净环境按文档启动；一段演示完整覆盖闭环；文档如实列出技术、能力、限制和已验证数据                          |
| **V2.x 移动端探索**（可选）            | Expo/RN、跨端 API 和 token 复用、移动端交互                  | 作为新的 `apps/mobile` 应用实现；复用接口和纯业务逻辑；重新设计原生 UI 与预览体验，不承诺 DOM 组件直接复用  |

### 每个版本的通用验收门槛

1. 版本有清楚的用户可见能力，不以新增空文件/框架依赖作为完成。
2. 至少有一条端到端演示路径；涉及逻辑的部分按风险补单元/API/组件测试。
3. 更新本文件中的状态、实际目录/接口和已知限制；重要架构改变写一条短 ADR。
4. 提交说明包含运行方式、验证记录、截图或日志（适用时）以及下一版本入口。
5. 只有实际运行和验证过的能力才标记为完成或写进简历。

## 5. Agent 与数据流程

阶段性目标流程：

```text
用户需求
   ↓
输入校验 / 需求结构化
   ↓
精选组件参考检索 ──→ 来源、许可证、检索理由
   ↓
生成 React + TypeScript 组件（结构化输出）
   ↓
静态/格式校验 → 隔离预览构建 → 诊断
   ↓                              ↘ 有界修复（达到上限即返回错误）
返回代码、预览状态、来源和可观察步骤
   ↓
用户继续对话 → 使用当前版本和本轮反馈进入下一次迭代
   ↓
保存版本 / 导出源码
```

关键工程约束：

- Agent 由明确的输入、状态、步骤、工具、输出组成；“一次 LLM 请求”先称生成服务，不夸大为自主 Agent。
- 每个工具只做一件可审计的事；模型不得自行获得文件系统、网络或命令执行权限。
- 生成次数、校验/修复轮数、执行时间、输出大小和依赖集合均有限制。
- 保存检索来源、模型/提示词版本、校验结果和修复次数，便于解释问题和复现。
- 先对小型固定数据集做离线案例评估；结果指标使用实际运行样本，不写臆测准确率。

## 6. 与项目结合的学习路线

| 项目阶段  | 学习主题                              | 做完应能解释的问题                                                                   |
| --------- | ------------------------------------- | ------------------------------------------------------------------------------------ |
| V0.1      | HTTP、CORS、FastAPI、React API 状态   | 请求从浏览器到 Python 服务经过哪些层？错误如何被前端识别？OpenAPI 如何成为接口契约？ |
| V0.2      | LLM API、提示词、结构化输出、Pydantic | 普通文本输出为何不够稳定？如何校验/拒绝不符合契约的结果？密钥与超时如何处理？        |
| V0.3      | TSX 编译、预览执行边界                | 编译器给出的错误如何映射到用户？隔离边界保护什么、不能保护什么？                     |
| V0.4      | RAG、元数据过滤、来源与评估           | 检索质量怎样衡量？为什么许可和来源要作为一等数据？何时向量库才有价值？               |
| V0.5      | LangGraph 状态图、重试、持久化语义    | 哪些步骤确定性、哪些由模型决定？分支条件是什么？循环如何有界？                       |
| V0.6–V1.0 | 数据建模、Agent Evals、追踪、部署     | 如何判断改动真的改善了系统？如何复现一次失败？简历指标的样本和口径是什么？           |

完成后请对照蓝图验收；只有阶段目标或架构路线发生变化时才建议更新蓝图，README/ADR 按实际需要更新

如本轮由开发者手动实现，再补充：“请给我逐步操作步骤和每步预期信号，不要替我运行命令或直接改文件。”

## 7. 五天集中开发的现实目标

若连续投入约五个工作日，目标定为**可演示的 MVP 候选版**，不是生产就绪产品。建议依次完成：

| 日程    | 主要产出                                 | 学习/验收重点                                  |
| ------- | ---------------------------------------- | ---------------------------------------------- |
| 第 1 天 | V0.1 API 垂直切片                        | 前后端契约、加载/错误状态、干净启动            |
| 第 2 天 | V0.2 模型生成                            | 结构化响应、后端密钥、失败与超时处理           |
| 第 3 天 | V0.3 预览技术验证和组件工作区            | 先验证运行隔离方案，再做组件代码与编译反馈     |
| 第 4 天 | V0.4 精选参考检索 + V0.5 最小工作流      | 来源可见，明确状态与有界修复；不追求通用 Agent |
| 第 5 天 | V0.6 最小保存导出、回归用例、README 演示 | 完整闭环可复现；按事实整理项目展示和简历描述   |

如预览隔离或模型接入出现未知技术风险，优先保证 V0.1–V0.4 的真实闭环，并把未完成部分留在后续版本；不要为赶进度宣称已经有安全沙箱、RAG 或自主 Agent。

## 8. 安全、质量与交付要求

- **密钥：** 仅后端环境变量；提交前检查忽略规则，不把密钥打包到前端构建产物。
- **生成代码：** 视为不可信输入；不在 API 进程或主 Web 页面中执行。预览技术验证通过前，只显示代码，不执行代码。
- **外部代码：** 只收录来源、许可证、依赖和采集时间可追踪的资料；遵守许可证和来源要求。
- **接口：** 限制输入长度，设置超时，规范错误结构；CORS 仅允许开发/部署所需来源。
- **质量：** 关键纯逻辑有单测；API 合同有集成验证；生成工作流有固定回归案例；UI 有一次完整人工演示检查。
- **可观测性：** 记录 request/session ID、工作流阶段、耗时、检索来源 ID、验证/重试结果；默认不记录不必要的用户敏感内容。
- **作品集：** README 有架构图、启动步骤、环境变量说明、核心能力、演示截图/视频和已知限制。
- **简历：** 只写已实现并可现场演示的 React、FastAPI、Agent、检索、验证、安全隔离或部署能力；没有测量依据时不写性能/准确率数字。

## 10. 蓝图维护规则

- 这是项目蓝图，记录**目标、阶段、验收和决策**，不作为每日进度表，也不把每个实现细节写死。
- 在里程碑收尾或项目方向、架构边界明显变化时复查；无需每次功能迭代都更新本文。
- 每个功能版本的具体状态、验证证据和遗留问题由该版本的开发记录、提交和 README 承载。
- 新增框架、基础设施或顶层目录前先说明对应的验收目标；若未来收益不清晰，延后。
- 项目用户流程、前后端职责、`uv` 管理 Python、React 组件为生成目标这些决策若要改变，先更新本文和 ADR，再开始对应实现。
